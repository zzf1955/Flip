## 背景

当前仓库已经有现成的 `training_data/pair/h2r/1s/<task>/` 配对数据，其中 `control_video/`
是 human 条件视频，`video/` 是 robot 目标视频，`manifest.jsonl` 还能回溯到对应的
`training_data/seedance_direct/1s/...` human 源和 `training_data/segment/...` robot 源。
这为一个 Masquerade 风格的“直接渲染机器人”baseline 提供了现成输入。

Masquerade 的核心不是外部人工标注，而是从 human 视频中估计手部/手臂的 bbox、关键点、
mask 和轨迹，再结合机器人模型、相机标定和运动学/控制把 robot 渲染回视频。对 FLIP
而言，我们要把这个 baseline 放在现有 h2r pair 数据上，与当前三阶段生成式 h2r 方法
做可比对照。

## 目标

在现有 h2r pair 数据上实现并跑通一个 Masquerade 风格的直接渲染 baseline：

1. 以 `pair/<data_type>/1s/<task>/control_video/pair_XXXX.mp4` 作为 human 输入。
2. 从 human 视频中自动提取手部/手臂相关信息，生成渲染所需的 pose / mask / 轨迹。
3. 使用现有机器人数据、机器人模型与相机内外参渲染 robot 视频。
4. 输出可与当前三阶段生成式 h2r 结果直接对比的 baseline 视频与对比产物。

## 范围

- 只覆盖现有 `training_data/pair/h2r/1s/` 下的配对数据。
- 默认优先跑当前 h2r 评测关注的任务集合，任务列表保持可配置，避免把任务逻辑写死。
- 复用现有机器人模型、相机标定、`segment` 侧 robot 资源和 `pair` 侧 human 视频，不引入
  EPIC 特定数据流。
- 只做 Masquerade-style direct render baseline 和对应的对比产物，不改当前三阶段生成式方法
  的训练/推理逻辑。
- 不要求新的人工标注；human 侧的 bbox / mask / pose / 轨迹应从 `control_video` 中自动提取。

## 实施计划（分步骤）

1. 梳理现有 h2r pair 的输入契约，明确 `manifest.jsonl`、`pair_order.jsonl`、`control_video/`
   和 `segment/` 侧 robot 源的对应关系。
2. 设计并实现 human 侧提取链路：从 `control_video` 自动得到手部/手臂 bbox、mask、关键点
   和用于渲染的轨迹或末端目标。
3. 设计并实现 robot 侧渲染链路：读取现有机器人模型、机器人 pose 资源和相机内外参，
   生成与原视频视角一致的 robot 渲染结果。
4. 组装 baseline 输出：将渲染 robot 结果和对应 human 输入、GT robot 目标写到统一目录，
   便于和当前三阶段生成式 h2r 结果逐样本对照。
5. 为 baseline 增加最小 smoke 测试和输出校验，确保任一缺失的输入都会直接失败。
6. 更新文档，补充该 Masquerade baseline 的数据流、输入依赖、输出路径和评测口径。

## 验收标准

- 能对至少一个现有 h2r task 跑通 baseline 生成，输出非空 robot 视频。
- baseline 输出能按 `pair_id` 或 `source_id` 回溯到原始 `control_video` 和 robot source。
- human 侧提取结果来自视频自动估计，不依赖额外人工标注。
- 在相同 pair 上能够生成与当前三阶段 h2r 结果并排对比的产物。
- 缺少关键输入时直接报错，不做隐式 fallback。

## 测试要求

- 至少对 1 个 task、少量 pair 做 smoke 跑通，确认输出视频帧数、分辨率和对齐关系正确。
- 验证 baseline 产物能按 manifest 重新定位到原始 human / robot 源。
- 验证缺失相机参数、机器人资源或 human 视频时脚本会失败。
- 若实现中新增脚本或配置，需补充对应 `doc/step_5_training_infra.md` 与 `doc/scripts_inventory.md`
  说明。
